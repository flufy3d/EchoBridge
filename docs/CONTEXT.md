# EchoBridge 上下文与记忆设计（讨论稿）

> 状态：讨论稿，尚未实施。先对齐问题、方案空间和取舍，再决定实现顺序。
>
> 代码基线：`src/echobridge/session.py` 的 `_history`、`_trim_history()`、`_build_llm_messages()`；`src/echobridge/manager.py` 的会话生命周期。

---

## 1. 现状

| 项 | 当前实现 |
|---|---|
| 存储位置 | `Session._history`，仅网关进程内存 |
| 生命周期 | 每次 WSS 连接 + `session.create` 新建 `Session` |
| 写入内容 | user ASR 文本、assistant 最终文本、assistant `tool_calls`、`role=tool` 结果 |
| 不写入 | greeting、`reasoning_content`、音频、base64 |
| 请求结构 | `system`（`session.create.instructions` + 实时语音约束）+ `_history` |
| 上限 | 最近 60 条消息，按条数截断 |
| 压缩 | 无。超过 60 条直接丢最旧消息 |
| 持久化 | 无。重连、休眠恢复、网关重启都会清空 |
| 设备端 SQLite | 只做记录，不回传网关作为上下文 |
| tool 链保护 | 截断后若头部是 `role=tool`，继续丢弃，避免从 tool 结果中间开始 |

换算：

- 纯聊天：1 轮 = user + assistant = 2 条 → 约 30 轮后开始遗忘。
- 带工具：1 轮约 4 条（user + assistant(tool_calls) + tool 结果 + assistant 最终文本）→ 约 15 轮后开始遗忘。
- `llm_max_tokens=400` 只是单次输出上限，不影响上下文预算。
- 没有 token 计数。60 条短语音消息通常远小于模型窗口，但如果单条 ASR 很长、工具结果很大，仍可能膨胀。

## 2. 先把三个问题拆开

这三件事经常被混在一起，但可以独立解决：

| 层 | 要解决的问题 | 关键指标 |
|---|---|---|
| 工作上下文 | 当前这一轮，模型应该看到什么 | 首音延迟、token 预算、tool 链完整 |
| 会话连续性 | 断线/休眠/重连后，能不能接着聊 | 记忆召回、恢复延迟、存储可靠性 |
| 长期记忆 | 跨天/跨会话记住用户、关系、事件 | 召回率、准确率、隐私、可删除 |

“压缩”主要解决第一层；“持久化”主要解决第二层；“事实/画像/检索”主要解决第三层。可以分阶段做，不必一次上全套。

---

## 3. 约束与目标

- **延迟优先**：首音 p95 目标 < 2.5 s。摘要不能卡在 ASR final → LLM 的关键路径上。
- **显存紧张**：RTX 3070 8 GB 已被 ASR/TTS 占用；不要再常驻一个本地摘要/embedding 大模型。短文本 embedding 可以考虑 CPU 或按需加载。
- **成本可控**：摘要和多一轮 LLM 调用都会增加 token；利用 DeepSeek 的 prefix cache，保持稳定前缀。
- **隐私**：只存文本，不存音频/base64/key；落盘要能删除、能设保留期；日志继续脱敏。
- **协议稳定**：设备端是 Android 9 + 老 WebView，改动成本高；优先网关侧实现，设备端最多加一个“清除记忆”开关。
- **单设备单会话**：当前 `SessionManager` 只允许一个活跃设备；记忆先按 `device_id` 隔离。
- **身份可信度**：`device_id` 来自客户端 header/query，不是强认证；未来多设备时要改成 token 绑定身份。
- **可运维**：单机 WSL2/systemd，优先 SQLite/JSONL，不引入 Postgres/Redis。
- **质量**：摘要不能编造事实；用户说“记住……”不能被当成系统指令；记忆要标注“可能过时”。

## 4. 持久化方案

### 4.1 记忆形态

| 方案 | 做法 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| A. 不持久化 | 现状 | 零存储、零隐私风险、最简单 | 重连即失忆 | 当前 |
| B. 原始转录落盘 | 每轮写 JSONL/SQLite；重连加载最近 N 条/N tokens | 简单、确定、无 LLM 成本、可审计 | 存储增长；旧内容仍会被截断；无长期画像 | 先修“重连失忆” |
| C. 会话摘要落盘 | 会话结束/阈值时生成摘要；重连加载摘要 + 最近 N 条 | 有长期连续性；prompt 有界 | 有损、摘要漂移、多一次 LLM 调用 | 长会话 |
| D. 结构化事实/画像 | 抽取姓名、偏好、关系、习惯、约定，存 JSON/表 | 高信号、token 少、可编辑/删除 | 抽取错误、冲突合并、需要维护 | 个性化 |
| E. 每会话/每日回顾 | 每个 session 或每天生成几条“发生了什么” | 时间线清楚、比全文短 | 冗余、细节少 | 跨天连续 |
| F. 向量检索（RAG） | 每轮/每段 embedding；按当前话检索 top-k | 可扩展到很长历史；只取相关 | 检索延迟、误召回、需要 embedding 模型/索引 | 大量历史 |
| G. 知识图谱/实体记忆 | 人物、地点、事件、关系建图 | 多跳、精确更新 | 工程量大、抽取复杂 | 复杂角色/长期关系 |
| H. 设备端存储 | App SQLite 保存，`session.create` 注入紧凑记忆块 | 网关无状态、隐私在设备、用户可清 | 要改 App；2 GB 设备；多设备不共享 | 隐私优先 |
| I. 混合 | 服务端 raw + summary + facts + 可选检索 | 兼顾连续性和个性化 | 最复杂 | 长期目标 |

### 4.2 存储介质

| 介质 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| JSONL 追加文件 | 零依赖、可读、易备份/删除 | 查询弱、并发写要加锁、易碎片 | v1 最快落地 |
| SQLite | 标准库、事务、索引、TTL 查询 | schema/迁移要设计 | 推荐正式方案 |
| Postgres | 强查询、多设备 | 运维重 | 当前不需要 |
| Redis | 快、TTL | 持久化/运维、重启风险 | 当前不需要 |

推荐路径：`var/memory/`（已在 `.gitignore`）或 `/var/lib/echobridge/memory/`；目录 700，文件 600。写入用临时文件 + rename，避免半截文件。

### 4.3 存什么、不存什么

**存：**

- `device_id`、`session_id`、`turn_id`、时间戳
- user 文本、assistant 文本
- tool 名称、参数摘要、结果摘要（可选）
- `interrupted`、`canceled`、`empty` 等状态
- ASR 语言/置信度（如果后续有）
- summary、facts、summary 模型/版本/时间

**不存：**

- 音频、base64、Authorization、API key
- 完整原始工具大结果（除非调试需要，且单独设短 TTL）
- 用户明确要求删除的内容

### 4.4 生命周期与作用域

- **作用域**：先按 `device_id`；未来多设备再引入 `user_id`/`persona_id`。注意 `device_id` 目前可伪造。
- **保留期**：7 / 30 / 90 天三档；默认 30 天；原始转录和摘要可以不同 TTL。
- **容量**：每设备最大 MB/条数，超限先删最旧原始记录，保留摘要/facts。
- **删除**：提供网关管理命令或 API；设备端设置页做“清除记忆”；删除要同时清 raw、summary、facts、索引。
- **加密**：如果威胁模型包含主机磁盘泄露，用 SQLCipher 或 age 加密；当前单机可信环境可以先不做，但要在文档里明确。
- **迁移/备份**：schema version；启动时迁移；备份只备份文本库。

## 5. 压缩方案

### 5.1 压缩策略

| 方案 | 做法 | 优点 | 缺点 | 适合 |
|---|---|---|---|---|
| 1. 条数截断 | 现状，保留最近 60 条 | 极简、零成本 | 预算不可控、突然失忆 | 当前 |
| 2. Token 预算滑动窗口 | 按 token 保留最近 N；在 turn 边界切 | 预算确定、实现简单 | 仍会丢旧信息 | 第一优先级 |
| 3. 滚动摘要 | 超出阈值时把最旧一段总结进 running summary | 长会话、prompt 有界 | 有损、摘要漂移 | 标准方案 |
| 4. 分层摘要 | turn → session → day/week 多层 | 兼顾细节和长期 | 工程量大、层级维护 | 长期 |
| 5. 结构化事实抽取 | 只抽稳定事实/偏好/约定 | token 少、可编辑 | 丢失叙事细节 | 个性化 |
| 6. 摘要 + 事实混合 | 叙事摘要 + JSON facts | 兼顾连续性和高信号 | 两套逻辑 | 推荐长期 |
| 7. 检索代替压缩 | 全量存，按当前话检索相关片段 | 不丢信息、可扩展 | 延迟/误召回/索引 | 历史很长 |
| 8. 重要性评分 | 按实体、情绪、承诺、未解决问题打分保留 | 保留关键内容 | 评分本身可能错 | 辅助 |
| 9. 语义去重/去填充 | 去掉“嗯/好的/重复问候”等 | 省 token | 可能误删语气 | 辅助 |
| 10. 提取式压缩 | 选原句而非生成摘要 | 不幻觉、便宜 | 连贯性差 | 保守场景 |
| 11. Provider 缓存/原生压缩 | 稳定前缀复用 cache；原生 compaction | 降延迟/成本 | DeepSeek 不一定支持；可移植性差 | 优化项 |
| 12. 小模型摘要 | 本地 0.6B/1.7B 或 CPU 模型 | 隐私、离线 | 显存/质量/维护 | 可选 |

### 5.2 推荐组合

**短期：Token 预算滑动窗口 + 完整 tool 链 + 保留最近 K 轮。**

**中期：滚动摘要 + 最近 8–12 轮原文 + 结构化 facts。**

**长期：如果召回测试证明不够，再加向量检索；不要一上来就 RAG。**

### 5.3 切分边界

压缩/截断必须以“完整 turn”为单位，不能从中间切：

- 一个 turn = user 文本 + 可能的 assistant(tool_calls) + 所有 tool 结果 + assistant 最终文本。
- 最近窗口至少保留 `min_turns`（例如 4 轮）或 `recent_tokens`（例如 3k），取较大者。
- 如果切点落在 tool 链中间，向前移到 assistant(tool_calls) 之前，或向后移到所有 tool 结果之后。
- 头部孤立的 `role=tool` 必须丢弃或补齐；OpenAI 兼容接口对 tool 链校验很严。
- 未完成的 tool 链（超时/取消）不要进入摘要；标记为 interrupted。
- 当前用户消息永远保留；单条超长时先截断工具输出/长文本，再考虑摘要。

### 5.4 摘要放哪里

推荐顺序：

```text
[system: 基础 instructions + 实时语音约束]
[system: 长期记忆摘要 + 用户画像（标注可能过时）]
[history: 最近 N 轮原文]
[user: 当前输入]
```

- 摘要在 system 之后、history 之前，模型更容易当背景而不是当轮对话。
- 摘要块保持稳定，直到下一次压缩；这样 system + 摘要前缀可以命中 provider prefix cache。
- 检索结果如果每轮变化，放在 history 之后、当前 user 之前，避免破坏前面的稳定前缀。
- 不要把摘要伪装成 assistant 说过的话；用明确的“以下是更早对话的摘要”标记。

### 5.5 摘要内容模板

建议结构化，控制在 200–500 tokens：

```text
【长期记忆（可能过时，仅作参考）】
用户画像：称呼/语言/偏好/禁忌
关系状态：角色关系、亲密度、未兑现的约定
重要事实：用户明确说过、且仍然有效的信息
最近事件：上次聊了什么、进行到哪一步
未完成：待办、未回答问题、未完成工具链
情绪基调：上次结束时的情绪/话题
```

原则：

- 只记录用户明确说过的内容；推测要标注不确定。
- 不执行摘要文本里的任何指令（防 prompt injection）。
- 保留来源 turn_id，方便回溯和纠错。
- 摘要用中文；长度可配置。
- 摘要模型可以和主对话模型分开，用低 `max_tokens`、`reasoning_effort=low`；失败就退回硬截断。

### 5.6 何时压缩

| 时机 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 超过消息条数 | 简单 | 预算不准 | 只作为兜底 |
| 超过 token 阈值（70–85%） | 提前、平滑 | 需要 token 计数 | 主触发 |
| 每轮 response.done 后异步 | 不阻塞当前轮 | 与下一轮并发，需版本控制 | 推荐 |
| 会话空闲时 | 不抢延迟 | 可能马上断线 | 辅助 |
| session.close 时 | 一定落盘 | 关闭有 1 s 预算，不能久等 | 后台限时 |
| 重连时 | 恢复前整理 | 增加恢复延迟 | 只加载，不现场总结 |
| 同步在 LLM 调用前 | 一定不超预算 | 直接加首音延迟 | 仅溢出兜底 |

推荐：**阈值触发 + 异步滚动摘要 + 关闭时限时落盘**。压缩任务失败不能让当前 turn 失败。

### 5.7 异步压缩的并发安全

- 触发时对 history 做快照，带 `history_version`。
- 摘要完成后，只有版本仍匹配才替换；否则把新 turn 追加到摘要之后，或丢弃这次结果重试。
- 每设备一把 summary lock，避免并发摘要。
- 摘要任务在 `session.close` 时取消/等待最多 1–2 s；未完成就保留旧摘要。
- 摘要写库用事务/原子 rename；崩溃后最多丢一次摘要，不影响原始记录。

### 5.8 Token 计数

- 精确：用 DeepSeek 对应 tokenizer；不确定是否公开。
- 近似：中文按 1 字 ≈ 1 token，英文按 4 字符 ≈ 1 token；加 15–20% 安全余量。
- 校准：请求加 `stream_options: {"include_usage": true}`，用返回的 `prompt_tokens` 校准估算；不同模型分开系数。
- 预算：`system + tools + summary + recent + current + max_tokens` 全部计入，不要只算 history。

### 5.9 失败与降级

- 摘要超时/报错 → 本次不压缩，改用 token 窗口硬截断；记录 metric。
- 摘要结果为空/明显跑题 → 丢弃，保留旧摘要。
- 存储损坏 → 以空记忆启动，日志告警，不阻塞会话。
- 摘要与最近原文冲突 → 以最近原文为准；摘要标注“可能过时”。

## 6. 组合方案与工作量

### 方案 A：最小闭环（推荐先做）

- 原始 turn 落盘（SQLite/JSONL），按 `device_id` 隔离。
- 重连时加载最近 N tokens / K 轮，而不是固定 60 条。
- 引入 token 预算截断，保留完整 tool 链。
- 不做摘要，不做 facts。
- 工作量：约 1–2 天；风险低。
- 解决：重连失忆、60 条上限不可控。
- 不解决：30 轮后旧内容仍会丢；没有跨天个性化。

### 方案 B：标准长会话

- A + 异步滚动摘要 + 摘要落盘。
- 保留最近 8–12 轮原文（约 3k tokens）+ 摘要（约 300–500 tokens）。
- 阈值 70–85% 触发；session.close 限时 flush。
- 工作量：约 3–5 天；风险中。
- 解决：长会话、跨会话连续性。
- 风险：摘要漂移、额外 LLM 调用、异步竞争。

### 方案 C：长期人格记忆

- B + 结构化 facts/画像 + 可选向量检索。
- 记录称呼、偏好、关系阶段、承诺、重要事件；注入紧凑 profile。
- 检索只在“上次/之前/还记得”等触发或低置信时使用。
- 工作量：约 1–2 周；风险高。
- 解决：跨天个性化、角色关系一致性。
- 风险：错误记忆、隐私、复杂度、检索延迟。

### 对比

| 能力 | A | B | C |
|---|---|---|---|
| 重连连续 | ✅ | ✅ | ✅ |
| 30+ 轮不遗忘 | 部分 | ✅ | ✅ |
| 跨天记得用户 | ❌ | 部分 | ✅ |
| 角色关系/约定 | ❌ | 部分 | ✅ |
| 首音延迟影响 | 极小 | 小（异步） | 小–中 |
| 实现复杂度 | 低 | 中 | 高 |
| 隐私/删除复杂度 | 低 | 中 | 高 |

## 7. 推荐路线

1. **Step 0：Token 预算 + 截断边界**
   - 先不加摘要，只把“60 条”换成“预算内最近 N 轮”。
   - 修 tool 链边界、超长工具输出、当前用户必保留。
   - 这是所有后续方案的基础。

2. **Step 1：原始历史落盘 + 重连加载**
   - SQLite 或 JSONL；按 `device_id`；默认 30 天。
   - 重连只加载最近 K 轮/tokens，不加载全部。
   - 这一步就能解决最大的体验问题：断线/休眠后失忆。

3. **Step 2：异步滚动摘要 + 会话结束摘要**
   - 超过阈值后台总结最旧一段；保留最近原文。
   - 摘要落盘，重连时和最近原文一起加载。
   - 加 metrics：压缩次数、耗时、摘要 tokens、失败次数。

4. **Step 3：结构化 facts/画像**
   - 先做少量高价值字段：称呼、语言、偏好、禁忌、关系阶段、未完成约定。
   - 人工可编辑/可删除；冲突以新事实为准并保留来源。

5. **Step 4：检索（可选）**
   - 只有当召回测试证明“摘要 + 最近原文”不够时才做。
   - 优先本地 CPU embedding + sqlite-vec/FAISS；不要占用 GPU。

## 8. 需要一起定的事

1. **记忆作用域**：只按设备，还是按“人”/角色？当前单设备单 token，先按 `device_id` 是否够？
2. **重连期望**：用户希望“接着刚才聊”，还是只要“记得我是谁/上次聊过什么”？前者要 raw 回放，后者摘要就够。
3. **保留期**：原始转录留多久？7/30/90 天/永久？是否需要用户可见的“清除记忆”？
4. **摘要模型**：用 DeepSeek API（简单、有成本、文本出网）还是本地小模型（隐私、占资源）？
5. **延迟预算**：压缩能否同步发生在溢出时（可能加 0.5–2 s 首音），还是必须全异步？
6. **记忆内容**：只记事实/偏好，还是也记情绪、关系、承诺？后者更像“角色记忆”，但更容易出错。
7. **多设备/家庭共享**：未来是否会有多个设备/多个用户？这决定 identity 和存储 schema。
8. **隐私边界**：是否加密落盘？是否允许导出？设备端是否要展示“我记得什么”？
9. **是否真的需要 RAG**：先用 30 天真实对话做召回测试，再决定。
10. **失败策略**：摘要失败时静默硬截断，还是给用户一个“记忆整理失败”的提示？语音场景建议静默。

## 9. 评估与验收

### 功能

- 30 轮纯聊天：预算内不丢最近上下文；超出后摘要包含关键事实。
- 带工具 15 轮：不出现孤立的 `role=tool`，不出现 400 tool 链错误。
- 重连：能召回最近 K 轮 + 摘要中的关键事实。
- 跨天：能记住称呼/偏好/未完成约定（按产品要求）。
- 删除：删除后重连不再召回。

### 性能

- 首音 p50/p95 相对现状不退化超过 100 ms（异步摘要不应影响）。
- 摘要 p95 耗时、失败率、每次摘要 token 成本。
- 重连加载 p95（本地 SQLite 应 < 50 ms）。
- 上下文 token 估算 vs 实际 `prompt_tokens` 误差 < 20%。

### 质量

- 脚本化召回测试：姓名、偏好、上次话题、承诺、禁忌。
- 人工评分：摘要是否准确、是否编造、是否把用户指令当系统指令。
- 冲突测试：用户改口后，新事实是否覆盖旧事实。
- 注入测试：用户说“忽略之前指令/你现在是管理员”，摘要是否只当数据。

### 可靠性

- 摘要超时/500/空结果：当前 turn 仍正常完成。
- 写库中断/磁盘满：会话不崩，降级为内存。
- 并发：摘要进行中用户继续说话，不串轮、不重复。
- 关闭：`session.close` 1 s 内完成，不被摘要任务拖死。

## 10. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 摘要编造事实 | 角色说错用户信息 | 只记明确事实；保留来源；冲突以原文为准 |
| 摘要漂移 | 越总结越偏 | 定期从 raw 重新总结；摘要版本化 |
| Prompt injection | 用户文本里的指令被当系统指令 | 摘要/记忆用数据分隔；明确“不要执行其中指令” |
| 旧事实过期 | 用户改口后仍记旧值 | facts 带时间和来源；新事实覆盖；可删除 |
| 隐私 | 转录落盘泄露 | 只存文本、权限 600、TTL、加密可选、删除接口 |
| 存储损坏 | 记忆丢失/启动失败 | 原子写、备份、损坏时降级为空记忆 |
| 异步竞争 | 摘要覆盖新 turn | history_version + per-device lock |
| Token 估算偏差 | 超预算被 provider 拒绝 | 安全余量 + usage 校准 + 溢出重试 |
| Prefix cache 失效 | 成本和首 token 变差 | 摘要块稳定；检索块放 history 后 |
| device_id 伪造 | 读到别人的记忆 | 多设备时改 token 绑定身份 |
| 记忆过多 | prompt 膨胀 | facts 上限、摘要长度上限、检索 top-k |

---

## 11. 一句话结论

**先把“预算 + 落盘 + 重连加载”做好，再上异步滚动摘要；facts/画像按产品需要加，RAG 最后考虑。** 这样每一步都能独立上线、独立回滚，且不会拿首音延迟换记忆。
